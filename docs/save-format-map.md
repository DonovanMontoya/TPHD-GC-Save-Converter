# Twilight Princess Save Format Map

This project treats TPHD -> GC conversion as a schema translation problem.
The converter must never assume byte compatibility unless a field is mapped.

## Sources

- GC target layout: `dSv_save_c` from the TP decomp. A GC quest log is `0xA94`
  bytes: `0xA8C` bytes of data plus two big-endian checksum words.
- TPHD source layout: observed from `ZTPxx.dat`. A TPHD slot is `0xE00` bytes:
  `0xDF8` bytes of data plus two big-endian checksum words.
- GCI wrapper: Dolphin `.gci` template is kept intact; only selected quest-log
  data and that slot checksum are rewritten.
- GC reference saves: the Any% pack contributes 45 valid quest-log slots, and
  the 100% NTSC-U 6.17.20 pack contributes 60 valid quest-log slots. Their
  summaries are saved in `docs/gc-anypercent-summary.csv` and
  `docs/gc-100percent-summary.csv`.

## Current Understanding

The first two TPHD bytes are not part of GC `dSv_player_status_a_c`.
GC expects max life at offset `0x000`, but TPHD stores it at `0x002`.

`exported-schema-safe.gci` has been tested in Dolphin and loads. That confirms
the GCI wrapper, checksum generation, player identity fields, and mapped
`status_a` block are load-safe for the current sample.

`exported-schema-balanced.gci` and `exported-schema-progress.gci` have been
tested in Dolphin and do not load. Probe exports in `probe-exports/` isolate
each additional copied group on top of the known-good safe profile.

`docs/gc-reference-audit-slot0.csv` compares the current sample's mapped TPHD
fields against all 105 valid GC reference slots. Probe testing has now shown
that `player.return_place` is a direct-copy failure, while `player.status_b`,
`player.items`, and `player.get_item_flags` load individually.
`exported-balanced-minus-return.gci` also loads, confirming the current
balanced group set is loader-safe once `player.return_place` is excluded.
`exported-progress-minus-return.gci` loads too, as does `probe-stage_memory.gci`,
`probe-visited_room_memory.gci`, and `probe-event_flags.gci`, so the current
structural progress blocks are loader-safe enough to parse. The reported
progress load is still missing Midna, which means semantic scene-state
translation remains incomplete.

Current TPHD body coverage, excluding checksum:

| Confidence | Bytes | Share |
| --- | ---: | ---: |
| observed | 826 | 23.1% |
| observed constant | 17 | 0.5% |
| structural | 1792 | 50.1% |
| sample zero | 926 | 25.9% |
| HD-only | 15 | 0.4% |
| unknown | 0 | 0.0% |
| mapped total | 2635 | 73.7% |
| classified total | 3576 | 100.0% |

`observed` means the field is named from the sample and/or has a clear GC
analogue. `structural` means the byte range has a GC-compatible struct envelope
at the same offset, but individual flags/bits still need validation.
`sample zero` means the range is zero in the current sample but needs more
saves before it can be called padding. `HD-only` means observed data with no
known GC destination. The coverage report is generated by `schema_coverage.py`
and saved in `docs/cemu-coverage.txt`.

Unsafe areas:

| Area | GC Offset | TPHD Offset | Reason |
| --- | ---: | ---: | --- |
| return place | `0x058` | `0x058` | direct-copy probe does not load; likely needs paired location/state translation |
| config/options | `0x1E0` | `0x1E0` | byte layout differs |
| reserve | `0x8F0` | `0x8F0` | TPHD sample contains extra stage/current-position data |
| HD tail | none | `0xA94..0xDF7` | no GC destination |

For the current sample, TPHD `player.return_place` and `hd.current_stage_name`
are both `F_SP121`. Generated load-safe GC files keep the template return stage
`F_SP103` and zeroed reserve bytes because direct TPHD return/current-state copy
is unsafe. This is the likely source of missing current-scene context such as
Midna.

Focused scene probes confirm the return field is the dangerous piece:
copying TPHD current-stage reserve bytes loads, but writing `F_SP121` into GC
`return_place` causes a full crash, and copying full TPHD `return_place` fails
to load. The newest probes therefore graft coherent `F_SP121` location bundles
from known-good GC reference saves instead of mixing a single return-stage field
with converted TPHD progress.

The Any% `F_SP121` location bundles load in the converted progress save, but
still miss sense/scent and the wolf multi-enemy attack. The 100% `Gorge Arc`
bundles do not load in this converted progress state. Current read: scene
loading and wolf ability restoration are separate mapping problems.

## Location State

Current location conversion is not solved yet. The field shapes are known from
the GC decomp, but the correct TPHD-to-GC translation is not a direct byte copy.

GC game start uses `player.return_place` directly:

| GC bytes | Meaning |
| ---: | --- |
| `0x058..0x05F` | return stage name |
| `0x060` | player status / start point |
| `0x061` | room number |
| `0x062..0x063` | unknown bytes, normally `0x15 0x00` in tested field saves |

For the current TPHD sample, the apparent return tuple is:

| Field | Value |
| --- | --- |
| stage | `F_SP121` |
| player status / start point | `0x06` |
| room | `0x03` |
| trailing bytes | `0x15 0x00` |

That exact 12-byte return tuple exists in the 100% `Gorge Arc` GC reference,
but grafting that reference's wider location bundle still does not load in the
converted progress state. This means the return tuple must be compatible with
other scene context, likely stage layer/progress/event state, not just valid on
its own.

Tested location outcomes:

| Probe | Result | Meaning |
| --- | --- | --- |
| direct TPHD `player.return_place` | does not load | unsafe |
| TPHD return-stage name only | full crash | stage name alone is unsafe |
| TPHD current-stage reserve block `0x8F0..0x93F` | loads | not enough to fix spawn/current scene |
| TPHD return stage plus current-stage reserve | full crash | current reserve does not make return-stage rewrite coherent |
| GC Any% `F_SP121` location bundle | loads | known-good GC location can be grafted |
| GC 100% `Gorge Arc` location bundle | does not load | exact matching return tuple is not sufficient |

Current converter behavior therefore keeps `player.return_place` and GC reserve
from the template. It preserves loader compatibility while leaving true current
location/spawn translation as an open mapping problem.

Wolf ability probes now graft targeted GC ability ranges on top of the
load-tested progress plus Any% `F_SP121` scene bundle. The likely candidate
ranges are item/get-item state `0x09C..0x0FF`, collect/light-drop state
`0x100..0x11B`, and event flags `0x7F0..0x8EF`. The tiny `player.wolf` range
at `0x110..0x113` is zero in the current TPHD sample and in the inspected GC
references, so it is unlikely to be the missing ability state by itself.

The GC decomp narrows the missing sense/scent and multi-enemy wolf attack
problem considerably. `dComIfGs_getCollectSmell()` reads selected equipment
index 3, so current scent is GC body `0x016`, not `player.collect`. Scent grant
code also sets the item-first bit and selected item slot 2. The GC ability
checks use event `F_0550 = 0x4308` for wolf sense and `M_015 = 0x0501` for
Midna's B charge attack. Targeted probes named `probe-ability_flags_*.gci` and
`probe-scent_*.gci` exercise those bits directly. Those probes have been
reported working for scent/sense on the current sample. The
`probe-ability_flags_midna_charge_ride.gci` result shows that `M_015 = 0x0501`
plus `M_067 = 0x0C10` restores the Midna multi-target attack. The converter now
derives this normalization in `balanced` and `progress` when TPHD has a known
scent item at source offset `0x018`.

Remaining non-GC / non-convertible TPHD ranges:

| Range | Size | Current read |
| --- | ---: | --- |
| `0x01E0..0x01EF` | `0x010` | TPHD config/options |
| `0x08F0..0x093F` | `0x050` | HD current-stage/current-position block |
| `0x0A99..0x0AA4` | `0x00C` | late-game HD-only block |
| `0x0AB8..0x0ABB` | `0x004` | common/late-game HD-tail flags |

Large areas requiring bit-level validation:

| Area | Offset | Size | Status |
| --- | ---: | ---: | --- |
| stage memory | `0x1F0` | `0x400` | structural |
| visited room memory | `0x5F0` | `0x200` | structural |
| event flags | `0x7F0` | `0x100` | structural |

## Tooling

- `save_schema.py` is the authoritative schema and conversion-rule list.
- `analyze_saves.py` prints field values and conversion-rule status for a
  TPHD slot and GC quest log.
- `analyze_cemu_collection.py` summarizes all valid `ZTPxx.dat` files under a
  folder. The current collection summary is `docs/cemu-collection-summary.csv`.
- `generate_byte_map.py` writes `docs/cemu-byte-map.csv`, the current complete
  TPHD byte map.
- `tphd_to_gci.py` uses `save_schema.py`; broad offset copies should not be
  added directly in the converter.

Run:

```bash
python3 analyze_saves.py CemuSave/1019e500/user/80000001/ZTP00.dat \
  "GameCubeSave/Card A/01-GZ2E-gczelda2.gci" --gc-slot 0
```

The sample output is saved in `docs/sample-analysis.txt`.

## Next Mapping Work

1. Create paired test saves where only one field changes: rupees, health, oil,
   equipped sword/shield/clothes, selected X/Y items, current stage, current
   room, spawn/start point, and one simple event flag.
2. Diff those saves with `analyze_saves.py` and promote TPHD fields from
   `unknown` or `unverified` to `observed` only when the offset is stable.
3. Build narrower location probes around the known-loading Any% `F_SP121`
   bundle: vary only return start point, only room, only field-last-stay, and
   only current-stage reserve bytes.
4. Validate event/stage flags against GC bit labels before enabling them in the
   default conversion profile.
5. Keep HD-only state explicitly dropped with report entries.
